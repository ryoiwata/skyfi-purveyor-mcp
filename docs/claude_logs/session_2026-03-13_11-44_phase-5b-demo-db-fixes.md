## Issues & Troubleshooting

### Issue 1: Confirmation URL returns 410 Gone

- **Problem:** Opening a confirmation URL generated by `purveyor demo` in a browser always returned HTTP 410.  Terminal 1 showed `"HTTP/1.1" 410 Gone` immediately after the URL was generated.
- **Cause:** `demo/agent.py` spawned the MCP server subprocess with `DATABASE_URL=sqlite+aiosqlite:///:memory:`.  The confirmation record was written into that in-memory database inside the subprocess.  When the browser hit `purveyor serve --local` (Terminal 1), that process queried its own `purveyor.db` on disk — the record was never there — so `get_confirmation_by_token` returned `None`, which maps to a 410 response.
- **Fix:** Changed the subprocess environment in `demo/agent.py` line 229 from `:memory:` to `sqlite+aiosqlite:///purveyor.db`.  Both the demo subprocess and the HTTP serve instance now read and write the same on-disk file, so the serve instance can find the confirmation record.

### Issue 2: `create_archive_order` tool fails with "internal configuration issue"

- **Problem:** The demo agent reported an internal error when calling `create_archive_order`, before even reaching the confirmation URL step.
- **Cause (historical):** The root cause chain was:
  1. Before commit `52ac25c`, `database.py` did not import `purveyor.models.tables`, so `Base.metadata` had no models registered.  `create_all` ran but created zero tables.
  2. The demo subprocess used `:memory:` (ephemeral), so Alembic migrations could not be applied against it.
  3. When the tool tried to `INSERT` into `order_confirmations`, SQLite raised "no such table", which propagated as an unhandled exception — the agent summarised this as "internal configuration issue".
- **Cause (structural):** `init_db()` called `create_all` unconditionally for all database backends, including Postgres, which should always use Alembic.  The intent was not clearly encoded.
- **Fix:** Rewrote `init_db()` to gate `create_all` on `":memory:" in url or url.startswith("sqlite")`.  SQLite (both in-memory and file-based) gets `create_all` for local-dev convenience; Postgres is explicitly a no-op.  Added a detailed docstring explaining why each branch behaves the way it does.

---

## Decisions Made

- **Use `purveyor.db` for the demo subprocess, not `:memory:`.**  The demo is designed to pair with `purveyor serve --local` (both terminals) for a complete confirmation flow.  Isolation was less valuable than shared state.  If the demo is ever run standalone, `init_db` + `create_all` still bootstraps the schema on first run.

- **`init_db` covers SQLite, Alembic covers Postgres.**  The project's documented workflow (`uv run alembic upgrade head` before `purveyor serve`) already implies Postgres is Alembic-managed.  Making this explicit in code removes ambiguity and prevents accidental `create_all` calls against a production schema.

- **Keep `create_all` for file-based SQLite (`purveyor.db`).**  Requiring `alembic upgrade head` before every `purveyor demo` run would be a poor first-run experience.  `create_all` is idempotent — it skips existing tables — so it is safe to call on a DB already managed by Alembic.
